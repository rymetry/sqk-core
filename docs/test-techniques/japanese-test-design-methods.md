# 日本発テスト設計技法 — テスト分析・観点体系化の方法論群

## エグゼクティブサマリ

本ドキュメントは、日本のテストコミュニティ(JaSST・WACATE・智美塾・テスト設計コンテスト等)で発展した、**テスト分析(テストベースを能動的に読む・テスト観点を体系化する)を明示的な工程として扱う方法論群**をまとめます。共通する問題意識は、仕様書の文をそのままテストケースに書き写す作業(西康晴が CPM 法=コピー&ペースト&モディファイ法と呼ぶもの)では、テストの意図が残らず、網羅の根拠も説明できない、ということです。各方法論は「テストケースを書く前に、何を・なぜテストするかを構造化する」ための異なる道具立てを提供します。

収録するのは出典検証済みの5系統です。(1) **3色ボールペンによる仕様書分析** — テストベースの読解を能動化するタグ付け法。(2) **テスト観点とテスト要求分析の概念**(智美塾) — 観点=テスト対象×テスト目的という定義と、テスト要求の源泉の分析。(3) **ゆもつよメソッド** — 論理的機能構造とテストカテゴリでテスト分析の一貫性を作る方法。(4) **HAYST 法とラルフチャート** — 6W2H から直交表までの組合せテスト設計体系。(5) **NGT/VSTeP** — テスト観点図・テストコンテナ・テストフレームによる観点の階層化とテスト開発プロセス。なお、ハブ不足領域リストに挙がっていた「Tiramis 8要素」「要求のメタモデル分析」は、公開一次出典を特定できなかったため本書には収録しません(§7)。

本リポジトリでの位置づけ: テストプロセス(TRA→TAD→TDD/TI→TE)の工程定義は[テスト活動プロセス調査まとめ](./test-process-research-summary-test-design.md)を、個別テスト技法の目録は[テスト技法スキルカタログ](./test-techniques-skill-catalog.md)を正とし、本書はその間を埋める**分析系・観点系の方法論**を、TRA(#1)・TAD(#3)スキルが参照できる形で文書化するものです。

## 1. 位置づけ — テスト分析を工程として扱う

ISO/IEC/IEEE 29119 や ISTQB もテスト分析・テスト設計を工程として定義しますが、日本のコミュニティは「テストケースの前段(何を・なぜテストするか)」の方法論化を特に厚く発展させてきました。背景にある典型的な失敗は次の2つです(西康晴の整理)。

- **CPM 法**: 仕様書の文をコピーして語尾を「〜すること」に変えるだけのテストケース作成。ケースは増殖するが、趣旨が分からないため終了判定も削減もできなくなる。
- **固定3レイヤー法**: 大項目・中項目・小項目の固定枠に無理に詰める整理。枠が観点の実態と合わず、粒度の混在と漏れを隠す。

本書の5系統は、この「意図の失われたテスト」への異なる処方です。テストベースの読み方を変える(§2)、観点という単位を定義する(§3)、分析の語彙を固定して一貫性を作る(§4)、対象のモデル化から因子を導く(§5)、観点の構造全体を設計対象にする(§6)、というアプローチの違いとして読むと使い分けやすくなります。

## 2. 3色ボールペンによる仕様書分析

齋藤孝の三色ボールペン法(客観的に最重要=赤、客観的にまあ重要=青、主観的に気になる=緑で文章に線を引く読解・情報活用法)を、仕様書の読み込みに応用したものです(ソフトウェア・テストPRESS Vol.2「3色ボールペンで読む仕様書」)。テスト分析での効能は、(1) 読むという受動的行為を、色を選ぶという判断の連続に変えること、(2) **客観(赤・青)と主観(緑)を明示的に分離する**こと、(3) 緑タグ(気になる・曖昧・矛盾)がそのまま仕様への質問リストの候補になることです。

本リポジトリの test-requirement-analysis(#1)スキルは、この考え方をテスト条件導出向けに適応した3色タグ付け(赤=仕様の重要箇所、青=構成要素、緑=疑問・矛盾)を内蔵しています。原典の赤・青が「客観的な重要度の2段階」であるのに対し、#1 の赤・青は「重要箇所/構造要素」という抽出対象の区別に再定義されている点が適応部分です。緑が主観・疑問の側に立ち、質問リストへ接続される構造は原典の応用と一致します。

## 3. テスト観点とテスト要求分析の概念(智美塾)

鈴木三紀夫の智美塾資料(JaSST'12 Tokyo)は、テスト要求分析(TRA)を「テスト要求の源泉を分析し、適切なテスト要求を開発する」活動として定義し、次の概念装置を与えます。

- **テスト観点 = テスト対象とテスト目的**。観点を扱いやすい粒度まで分解・体系化し、「何を」「どのような目的で」テストするかを明らかにする(例:「顧客情報登録機能の機能テストを行う」)。
- **テスト要求の源泉**: 開発側/テスト側それぞれの Policy(品質ポリシー・品質計画)・People(ステークホルダー・体制)・Process(標準・アプローチ)・Product(テスト対象・テストベース・過去の欠陥データベース)・Quality/Cost/Delivery(スキル・コスト・納期)を棚卸しする。仕様書だけがテスト要求の源泉ではない。
- **リスクの識別**: 要求リスク・技術リスク・スキルリスク・政治リスクを、テストアーキテクチャに影響するものとして TRA 段階で挙げる。
- テスト要求分析は一度で終わらず、**テスト活動中に繰り返し実行する**。

本リポジトリの #1 スキルの「3視点(ユーザー/プロダクト/テスト組織)でのテスト条件導出」と「質問リスト必須出力」は、この源泉分析・観点分解の運用形です。

## 4. ゆもつよメソッド

湯本剛が発展させたテスト分析の方法論で、**分析の語彙を先に固定することで、分析者ごとのばらつきを減らす**ことに特徴があります(智美塾 JaSST'13 の本人資料、WACATE 2014 入門資料)。

- **プロセス**: テスト分析は「実現したい品質の具体的把握 → テスト箇所の選択 → テストの目的設定」で始まり、「機能の整理&再分類 → テストタイプ特定 → テストカテゴリ作成 → テスト条件となる仕様項目特定 → テスト対象アイテム特定」と続く。テスト設計(設計方針特定→ケース条件特定→技法適用→ケース作成)とは工程として区別される。
- **論理的機能構造**: 機能を**入力・変換・貯蔵・出力・サポート**という論理要素で捉える固定モデル。仕様書の章立てではなくこの構造で機能を再分類することで、「どの機能でも同じ問いを立てる」ことができる(入力なら異常データ・量・サイズ・タイミング、貯蔵なら格納データサイズ・空き容量、など)。
- **テストカテゴリ**: 論理的機能構造の各要素に、テスト対象から見てふさわしい名前を付けたもの。テスト条件(仕様項目)を見つける際の一貫した解釈の枠になり、テスト条件は「○○な場合、××すると〜〜となる」という仕様項目×期待値の形で表現できる。

本リポジトリとの対応: #1(TRA)の詳細テスト条件導出、#3(TAD)のテストタイプ割当てに対する補助方法論として参照できます。#3 の構造化手順自体は test-process 文書の5切り口を正としており、ゆもつよメソッドはテストカテゴリという語彙固定のアプローチを提供する選択肢です。

## 5. HAYST 法とラルフチャート

HAYST 法は富士ゼロックスで開発された、直交表を用いる組合せテストの設計体系です(秋山浩一らによる。書籍『ソフトウェアテストHAYST法入門』日科技連 2007、『事例とツールで学ぶHAYST法』同 2014。以下は JaSST'18 Tohoku 基調資料に基づく)。ステップは **6W2H → FV表 → ラルフチャート → FL表 → 直交表への割付け**です。

- **6W2H**: テスト対象の全体像(誰が・何を・なぜ・いつ・どこで・誰に・どのように・どれだけ)を把握し、大規模・複雑なテスト対象を見通す。
- **FV表**: ユーザーストーリー(3W)から目的機能(Function)と検証内容(Verification)を整理し、テスト対象を小さく分割してから技法を割り当てる。
- **ラルフチャート**: 分割後のテスト対象(目的機能)を、**入力・出力・状態変数・ノイズ・アクティブノイズ**でモデル化する図。品質工学(タグチメソッド)の P-チャートの系譜で、信号因子=入力、誤差因子=ノイズ、状態因子=状態変数に対応する。モデル化した各要素の性質から因子が見つかり、因子の性質がそのまま技法選択に対応する(入力と出力が少なければ同値分割・境界値分析、有則の論理組合せなら原因結果グラフ・CFD法・デシジョンテーブル、無則の組合せなら HAYST法・直交表・Pairwise、状態変数の Read/Write が中心なら状態遷移、極限環境ノイズなら負荷テスト、など)。複数のラルフチャートの結合から、状態遷移や変数共有といった弱点箇所も見つけられる。
- **FL表**: 組合せテストを行うと決めた項目について因子・水準を整理する表。**水準1はデフォルト値とし、異常値は入れない**(異常値はエラー処理テストとして別に扱う)という規約が、組合せ爆発と有則/無則の混同を防ぐ。

本リポジトリとの対応: #3(TAD)での構造分割・厚み設計、#4(TDD/TI)での組合せ技法選択([テスト技法スキルカタログ](./test-techniques-skill-catalog.md)の組合せ系技法)の背景体系として参照できます。因子の性質→技法という対応表の考え方は、カタログの「状況→技法選択マトリクス」と同型です。

## 6. NGT/VSTeP — テスト観点・コンテナ・フレームの階層化

西康晴(電気通信大学)による、テスト観点を中心にテスト開発全体を進める記法と方法論です(本人公開資料、2013)。

- **NGT(Notation for Generic Testing)**: テスト観点図の記法。テスト観点を階層的に記述し、**詳細化関係**(継承・部分・属性化・原因結果などのステレオタイプで意味づけできる)、**組み合わせ関連**(組合せテストの必要性)、**順序依存関連**を線種で区別して表す。観点の例としては Ostrand の4ビュー、Myers のシステムテストカテゴリ、ISO/IEC 9126(現 25010)の品質特性などが観点源として挙げられ、単一の正しい観点リストがあるのではなく、対象に応じて観点図を構築する。
- **VSTeP(Viewpoint-based Software Test Engineering Process)**: テストケースを開発成果物と捉えるテスト開発プロセス。**テスト要求分析**(観点図を作りリファインする。ステレオタイプ分析・確定)→ **テストアーキテクチャ設計**(観点の剪定・ズームイン/ズームアウト、**テストコンテナ**への分割=テスト全体像の構成、**テストフレーム**の構築=観点の組をテストケースの雛形にする)→ テスト詳細設計 → テスト実装(集約)と進む。
- 観点図・コンテナ・フレームという3層は、本リポジトリの HTC/DTC(観点相当)→ TAE(コンテナ相当)→ TC(フレームから展開されるケース)という10ノードチェーンの構造とよく対応します。狙った観点を NGT で整理して蓄積すれば、次のプロジェクトで再利用できる、という資産化の考え方も VSTeP の一部です。

本リポジトリとの対応: #1(TRA)の観点分解、#3(TAD)の TAE 分割・割当マトリクスの設計判断(なぜこの分割か)を説明する語彙として参照できます。

## 7. 収録範囲と利用上の注意

- **収録見送り(出典未確認)**: 「Tiramis 8要素」「要求のメタモデル分析」は、2026-07-27 時点の公開検索で一次出典を特定できなかったため、本書には収録しません。検証経緯と再起票条件は [\_research/japanese-test-design-methods](../_research/japanese-test-design-methods/README.md) の研究カード(RC-JTD-006/007)に記録してあります。skills はこれらの手法を前提にしません。「要求のメタモデル分析」が指す実質(テスト観点の分解・体系化)は、§3 の確認済み範囲が部分的に代替します。
- **名前ではなく構造を使う**: 本書の方法論は語彙・図法が異なるだけで、「観点(何を・なぜ)を先に構造化し、ケースはそこから展開する」という骨格を共有します。AI エージェントが適用する場合も、手法名のラベル付けを成果とせず、(1) どの構造化装置(タグ・カテゴリ・チャート・観点図)を使ったか、(2) それによって何が発見されたか(疑問・欠落・因子・観点)を出力に残すことが本質です。
- **タグ・カテゴリの増改築に注意**: ゆもつよメソッドのテストカテゴリは「テスト対象に合わせて命名する」ことが前提ですが、3色タグや論理的機能構造・ラルフチャートの要素集合は固定して使うことで一貫性が生まれます。場当たりで色や要素を増やすと、分析結果の比較可能性が失われます(ODC のトリガー再定義禁止と同じ原理。[欠陥タクソノミーと ODC](../quality-management/defect-taxonomy-odc.md) 参照)。
- **出典の性質**: 本書の主要出典はコミュニティ・著者公開のシンポジウム資料であり、国際規格ではありません。規格上の工程定義・用語との対応が必要な場面では [テスト活動プロセス調査まとめ](./test-process-research-summary-test-design.md)・[テスト標準と保証概念](./testing-standards-and-assurance-concepts.md) を正とします。
