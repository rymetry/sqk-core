# コードレビュー技法 — レビュー体系・静的解析結果の解釈・所見の重大度付け

## エグゼクティブサマリ

コードレビューは、テスト実行より前に欠陥を検出できる数少ない品質活動であると同時に、**欠陥検出だけが目的ではない**活動です。Microsoft での大規模調査(Bacchelli & Bird, 2013)は、レビューの動機として欠陥発見が最上位に挙げられる一方、実際の成果はコード改善・代替案の発見・知識移転・チームの状況認識が大半を占めることを示しました。この「期待と実態のずれ」を理解しないままレビューを欠陥検出装置としてだけ運用すると、形式化した承認作業(rubber stamping)に退化します。

実務上の要点は四つです。第一に、**レビューはフォーマル度のスペクトラムを持つ体系である**ことです。IEEE 1028-2008 はマネジメントレビュー・技術レビュー・インスペクション・ウォークスルー・監査の5類型を定義し、ISO/IEC 20246:2017 と ISTQB がこれを現代のワークプロダクトレビュー一般へ引き継ぎました。目的(欠陥検出か、合意形成か、教育か)に応じて類型と厳格度を選びます。第二に、**モダンコードレビュー(MCR)の効果は変更サイズと速度に強く依存する**ことです。1回のレビュー対象は 200〜400 行以下、レビュー速度は毎時 500 行以下が実証研究の推奨であり、Google は「小さい変更・速いターンアラウンド」を制度として強制しています。第三に、**静的解析の所見は「解釈」してはじめて価値を持つ**ことです。SAST は誤検知率が高く、SCA は到達可能性を考慮しない検出が多いため、生の指摘件数ではなく、トリアージ(真陽性判定→悪用可能性→修正優先度)を経た所見だけをレビュー結果として扱います。第四に、**所見は重大度と根拠をセットで提示する**ことです。重大度のない指摘リストは受け手に優先順位判断を丸投げし、根拠のない指摘は信頼を毀損します。

本ドキュメントは、レビューの標準体系(§1)、モダンコードレビューの実証知見(§2)、観点の構造化(§3)、静的解析結果の解釈(§4)、所見の重大度付け(§5)、レビューコメントの書き方(§6)、AI エージェントがレビューを実施する際の適用境界(§7)を扱います。SAST/DAST/SCA そのものの特性比較と CI/CD 配置は[セキュア開発とサプライチェーン §6](../secure-development/secure-development-and-supply-chain.md#6-セキュリティテスト解析の使い分け)、品質ゲートとメトリクス運用は[品質管理実務リファレンス](./software-quality-management-practical-reference.md)、指摘件数の目標化が生む歪みは[品質メトリクスの落とし穴](./quality-metrics-pitfalls.md)を正とし、本ドキュメントでは重複させません。

## 1. レビューの標準体系

### 1.1 IEEE 1028-2008 の5類型

IEEE 1028-2008(IEEE Standard for Software Reviews and Audits)は、ソフトウェアレビューを目的とフォーマル度で5類型に分けます。この分類は「レビュー」という言葉で異なる活動を混同しないための語彙として今も有効です。

| 類型 | 主目的 | フォーマル度 | 主導者 | 典型的な出力 |
| --- | --- | --- | --- | --- |
| マネジメントレビュー | 進捗・計画・リソースの意思決定 | 中 | マネジメント | 是正処置・計画変更の決定 |
| 技術レビュー | 成果物の技術的適合性の評価・代替案の検討 | 中〜高 | 技術リーダー | 技術的所見・推奨事項 |
| インスペクション | 定義されたプロセスによる欠陥検出 | 最高 | 訓練されたモデレーター(作成者以外) | 欠陥リスト・欠陥データ・合否判定 |
| ウォークスルー | 理解の共有・教育・改善案の収集 | 低〜中 | 作成者 | コメント・改善提案 |
| 監査 | 規格・契約・法規制への準拠性の独立評価 | 最高 | 独立した監査人 | 準拠/非準拠の判定 |

インスペクションの原型は Fagan が IBM で確立した方式(1976)です。計画→概要説明→個人準備→インスペクション会議→修正→フォローアップの6段階と、役割分担(モデレーター・読み上げ役・記録役・作成者)、および読み上げ速度の統制を特徴とし、テスト前の欠陥除去率を大幅に高められることを実証しました。現代の MCR はこの厳格な会議方式をほぼ置き換えましたが、「作成者以外が主導する」「欠陥データを記録し再発防止に使う」というインスペクションの原則は、フォーマル度の高いレビューが必要な場面(安全関連システム、規制対応)で今も使われます。

### 1.2 ISO/IEC 20246 と ISTQB による現代化

ISO/IEC 20246:2017(Work product reviews)は、IEEE 1028 の系譜をソフトウェアに限らないワークプロダクト一般のレビュープロセスとして国際規格化したものです。ISTQB Foundation Level シラバス v4.0 はこれを参照し、レビュープロセスを**計画→レビュー開始→個人レビュー→課題の共有と分析→修正と報告**の5活動で定義します。実務上の含意は二つあります。(1) 個人レビュー(各自が事前に成果物を読む)を省略した「会議だけのレビュー」は欠陥検出力が大きく落ちる、(2) 課題の共有と分析で「欠陥か、質問か、改善提案か」を分類してから修正判断に進む——この分類が §5 の重大度付けの前段になります。

コードレビューをテストプロセス全体の中で見ると、静的テスト(テストベース確認・静的レビュー)の一部です。位置づけとパイプライン上の前後関係は[テスト活動プロセス調査まとめ §4.3](../test-techniques/test-process-research-summary-test-design.md#43-2-テストベース確認静的レビュー)を参照してください。

## 2. モダンコードレビュー(MCR)の実証知見

### 2.1 MCR の定義と収斂

現代の主流は、Fagan 式の会議型インスペクションではなく、**変更(diff)単位・ツール支援・非同期・軽量**のモダンコードレビューです。Rigby & Bird(2013)は、OSS・Microsoft・Google など背景の異なる複数組織を横断調査し、レビュー実務が「小さい変更を、少人数(2名以下)が、短いサイクルで見る」形へ独立に収斂したことを示しました。会議型との最大の違いは、欠陥検出単体の効率よりも、継続的・低遅延であることを優先する点です。

### 2.2 何が実際に得られるか — 期待と実態

Bacchelli & Bird(2013)が Microsoft の開発者・マネージャーを調査した結果、レビューへの期待(動機)の第1位は欠陥発見でしたが、実際のレビューコメントの成果は、コード改善(可読性・スタイル)、代替解法の提案、知識移転、チーム内の状況認識が中心で、深刻な機能欠陥の発見は相対的に少数でした。また、レビューの質を律速するのは**変更の理解(program comprehension)**であり、理解できない変更には表面的なコメントしか付かないことが示されました。この知見の実務的帰結は次の通りです。

- レビューを「欠陥ゼロの保証装置」として扱わない。深い欠陥検出はテスト・静的解析と分担する。
- 変更の説明(コミットメッセージ・PR 説明・自己レビューコメント)は、レビュー品質への投資として最も費用対効果が高い。
- 知識移転・設計合意という成果を「本来の目的ではない副産物」と見なさない。

McIntosh らの実証研究(2016)は、Qt・VTK・ITK プロジェクトにおいて、レビューカバレッジ(コミットのうちレビューされた割合)とレビュー参加度(議論の濃さ)が低いコンポーネントほどリリース後欠陥が多いことを示しました。「レビューされたか」だけでなく「どれだけ実質的に議論されたか」が品質と相関します。承認だけで議論のないレビューは、カバレッジ上は 100% でも品質効果を持ちません。

### 2.3 サイズと速度のガイドライン

SmartBear が Cisco で実施した大規模調査(2006、2,500 レビュー・320 万行)に基づく推奨と、Google の運用(Sadowski et al., 2018)は、次の点でほぼ一致しています。

| 項目 | 実証ベースの推奨 | 根拠 |
| --- | --- | --- |
| 1回のレビュー対象サイズ | 200〜400 行以下 | 400 行を超えると欠陥発見率が顕著に低下する(SmartBear/Cisco 調査) |
| レビュー速度 | 毎時 500 行以下 | 速いレビューは欠陥密度の検出が落ちる(同上) |
| 1セッションの時間 | 60〜90 分以内 | 集中力の持続限界(同上) |
| 変更サイズの制度化 | 小さい変更(small CLs)を規範として強制 | Google の変更サイズは中央値約 24 行・35% 超が単一ファイル変更(Sadowski et al.) |
| ターンアラウンド | 小さい変更で 1 時間未満(中央値) | レビュー遅延は変更の肥大化と迂回を誘発する(同上) |
| レビュアー数 | 通常 1 名で十分 | Google では大半の変更が 1 名のレビューで完結する(同上) |
| 作成者の事前準備 | 自己レビュー・変更説明の付与 | 変更理解がレビュー品質を律速する(Bacchelli & Bird) |

Google の運用でもう一つ重要なのは、可読性(readability)認定制度と機械化の分担です。言語ごとのスタイル・イディオムは認定制度と自動整形・lint に寄せ、人間のレビューは設計・正確性・保守性の判断に集中させています。「機械が判定できる指摘は機械に任せる」は、§4 の静的解析の分担と同じ原則です。

## 3. レビュー観点の構造化 — 正確性・セキュリティ・保守性

観点を持たないレビューは、目につくもの(タイポ・スタイル)に吸い寄せられ、重大な欠陥を素通りさせます。本リポジトリでは、レビュー所見を**正確性・セキュリティ・保守性**の3観点で構造化します。以下は Google のレビューガイド(What to look for)と OWASP Code Review Guide を3観点へ再整理したチェックリストです。

| 観点 | 代表的な確認項目 | 主な出典 |
| --- | --- | --- |
| 正確性 | 要求・仕様との一致/エッジケース(空・null・境界値・重複・順序)/エラー処理と例外伝播(握りつぶしの禁止)/並行性(競合・デッドロック・共有状態)/リソース管理(リーク・クローズ漏れ)/後方互換性・データ移行 | Google eng-practices(functionality)、[テスト標準と保証概念](../test-techniques/testing-standards-and-assurance-concepts.md) |
| セキュリティ | 入力検証(信頼境界の明確化)/認証・認可(権限チェックの漏れ・昇格経路)/秘密情報(ハードコード・ログ出力・エラーメッセージ経由の漏えい)/デフォルト値・フォールバック経由の秘密情報混入(設定欠落時のフォールバックにハードコードされた鍵・秘密を使わない)/インジェクション(SQL・OS コマンド・テンプレート)/アウトバウンド先 URL の検証(SSRF: ユーザー・テナント入力由来の宛先へのリクエストは内部ネットワーク到達性・スキーム・宛先の制限を確認)/暗号(自作暗号の禁止・鍵管理)/依存関係の追加(サプライチェーン) | OWASP Code Review Guide、OWASP ASVS、[セキュア開発とサプライチェーン](../secure-development/secure-development-and-supply-chain.md) |
| 保守性 | 設計(責務の分離・抽象の妥当性・不要な複雑さ)/命名・コメント(なぜ、を説明しているか)/テスト(変更に対応するテストの有無と質)/重複(既存実装の再利用可否)/ドキュメント(利用者向け文書の追随) | Google eng-practices(design, complexity, tests, naming, comments) |

運用上の原則を三つ挙げます。

1. **観点は毎回すべて確認する**のではなく、変更の性質から重み付けします。認可制御を触る diff はセキュリティ観点を最優先し、内部リファクタリングは正確性(挙動不変)と保守性を優先します。
2. **チェックリストは検出器であって上限ではありません**。チェックリスト外の違和感(この設計は将来の変更に耐えるか)を封じないこと。逆に、チェックリストを形骸化させないため、実際に流出した欠陥から項目を追加・削除する保守サイクルを持ちます。
3. **スタイル・フォーマットは観点に含めません**。自動整形と lint で機械化し、人間とツールの二重指摘を避けます(§2.3、§4.4)。

## 4. 静的解析結果の解釈

### 4.1 前提 — ツール特性の理解

SAST・DAST・SCA・secret scanning の検出対象・誤検知傾向・カバレッジ限界・実行タイミングの特性比較は、[セキュア開発とサプライチェーン §6](../secure-development/secure-development-and-supply-chain.md#6-セキュリティテスト解析の使い分け)を正とします。本節はその出力を**レビュー所見として解釈する**手順を扱います。前提となる特性は次の2点です。

- SAST は誤検知率が高めで、データフローの文脈(検証済み入力か、到達不能コードか)を見誤ります。生の指摘リストをそのまま修正要求にしてはいけません。
- SCA の検出は「依存に既知 CVE がある」ことしか意味しません。その脆弱な関数を実際に呼んでいるか(到達可能性)は別の判断です。

### 4.2 トリアージの手順

静的解析の指摘は、次の順で分類・削減してから所見化します。

1. **真偽判定**: 指摘ごとに真陽性(true positive)/誤検知(false positive)を判定する。誤検知はツール設定(ルール調整・除外)へフィードバックし、個別抑制コメントの乱用を避ける。
2. **該当性判定**: 真陽性のうち、当該コンテキストでリスクにならないもの(到達不能・別レイヤで対策済み・意図的な仕様)を「リスク受容」として理由付きで記録する。SCA の場合は VEX(当該製品では非該当という表明)を使う。
3. **優先度付け**: 残った指摘に修正優先度を付ける。セキュリティ指摘は CVSS(技術的深刻度)を基礎に、EPSS(悪用予測確率)と CISA KEV(悪用実績)で補正し、当該システムでの到達可能性・資産価値を加味する。CVSS 単独のスコア順修正は、悪用される可能性がほぼない指摘に工数を吸われる典型的な誤運用です。
4. **ベースライン管理**: 既存コードの大量の指摘(棚卸し残)と新規コードの指摘を分離し、ゲートは新規コードにのみ適用する(Sonar の Clean as You Code 方式)。既存分は計画的に返済する。

### 4.3 抑制の監査

指摘の抑制(suppress・ignore コメント、ルール無効化)は、正当な理由がある場合に限り、理由を残して行います。「静的解析指摘ゼロ」を目標化すると抑制コメントの乱用とルール無効化で数字だけが達成される力学は、[品質メトリクスの落とし穴](./quality-metrics-pitfalls.md#ソフトウェア開発におけるゲーミングの典型例)の通りです。抑制・例外の件数と理由は集計・監査の対象とし、レビューでは「抑制の追加」自体を所見対象(なぜ抑制で解決するのか)として扱います。

### 4.4 人間(または AI)レビューとの分担

静的解析と目視レビューは検出領域が異なります。構文パターンで表現できる欠陥(危険 API・既知の脆弱パターン・スタイル)はツールが人間より速く網羅的であり、要求との不一致・設計の不適切さ・ドメインロジックの誤りはツールには見えません。したがって、(1) ツールで検出できる指摘を人間が手動で探さない、(2) ツールが通ったことをもって設計・ロジックの正しさを推定しない、という双方向の非代替性を運用に織り込みます。静的解析結果が与えられていないレビューは、この片翼がない状態であり、その旨を成果物に明記します(§7)。

## 5. 所見の重大度付け

### 5.1 重大度スキーム

本リポジトリのレビュー所見は、成果物レビューの所見契約([artifact-review-finding schema](../../schemas/artifact-review-finding.schema.json))と同じ **blocker / major / minor / info** の4値を使います。コードレビューへの適用基準は次の通りです。

| 重大度 | 判定基準 | コードレビューでの典型例 | マージへの影響 |
| --- | --- | --- | --- |
| blocker | 出荷すると利用者・データ・セキュリティに実害が出る、または変更目的を達成していない | 正確性の欠陥(データ破壊・誤計算)、悪用可能な脆弱性、認可チェックの欠落、後方互換性の破壊 | 修正するまでマージ不可 |
| major | 実害の確度は blocker より低いが、放置すると欠陥・重大な負債になる | エラー処理の欠落、境界値の未考慮、テストの欠如、既知の競合条件、抑制コメントの説明なし追加 | 原則修正。例外はリスク受容の記録を条件に許容 |
| minor | 品質を下げるが実害への経路が限定的、または文書化済みトレードオフの範囲内 | 命名の不明瞭、重複コード、コメント不足、非効率だが正しい実装 | マージを止めない。nit として明示 |
| info | 修正を要求しない情報提供 | 改善提案、代替案の紹介、賞賛、学習リソースの共有 | 影響なし |

### 5.2 判定の軸と根拠の必須化

重大度は**影響度(それが起きたら何が壊れるか)と確度(本当に起きるか)の積**で判定します。運用原則は次の通りです。

- **すべての所見に根拠を付けます**。該当箇所(ファイル・行)と、blocker/major には「どの入力・状態で、何が起きるか」の失敗シナリオを必須にします。根拠を書けない指摘は、確信がないということであり、重大度を下げて質問(§6)として出します。
- **セキュリティ所見は一般則より一段慎重に扱います**。悪用可能性の判断には CVSS・EPSS・KEV・到達可能性(§4.2)を使い、判断がつかない場合は高い側に倒します。リリースゲートとの接続は[セキュア開発とサプライチェーン §10](../secure-development/secure-development-and-supply-chain.md#10-品質ゲートと証跡-リリース判定にセキュリティを組み込む)を参照してください。
- **重大度の一貫性を監査します**。重大度インフレ(通すべきでないものを通すための切り下げ)とデフレの力学は[品質メトリクスの落とし穴](./quality-metrics-pitfalls.md#重大度インフレとデフレ)の通りで、レビュー所見にも同じ圧力がかかります。blocker の解除は理由の記録を必須にします。
- **重大度と修正時期を分離しません**。「major だがいつか直す」は事実上の minor です。major 以上は当該変更内での修正か、期限と担当を持つ課題化のどちらかを明示します。

## 6. レビューコメントの書き方

レビューの成果はコメントを通じてしか伝わらないため、コメントの質はレビューの質そのものです。Google のレビューコメントガイドの原則は次の4点に要約できます。

1. **コードについて述べ、人について述べない**。「あなたはここで誤っている」ではなく「このコードは X の場合に Y になる」。
2. **理由を説明する**。「変更してください」ではなく、どの原則・どの失敗シナリオに基づく指摘かを書く。受け手が原則を学べるコメントは、次のレビューを不要にする投資である。
3. **重要度を明示する**。修正必須の指摘と好みの提案が同じ文体で並ぶと、受け手は全部に対応するか全部を無視するかに振れる。nit:(些末)のような接頭辞で明示する。
4. **賞賛を含める**。よい設計判断・改善への言及は、指摘の受容性を高めるだけでなく、よい実践を強化する。

これを構造化したのが Conventional Comments 形式です。ラベル(praise / nitpick / suggestion / issue / question / thought / chore)と修飾(blocking / non-blocking / if-minor)をコメント先頭に付けます。本リポジトリの重大度(§5.1)との対応は、issue (blocking)=blocker/major、suggestion (non-blocking)・nitpick=minor、praise / thought / question=info が基本です(question は回答次第で昇格します)。

```text
issue (blocking): この分岐は quantity=0 のとき除算例外になります。
入力検証を追加するか、0 を仕様として扱う根拠をコメントで残してください。

suggestion (non-blocking): この 3 箇所の変換は utils/normalize に既存実装があります。
再利用すると差分が小さくなります。

question: この再試行回数 5 は要件由来ですか?
根拠があれば定数名かコメントでの明示を提案します。
```

修正提案は、可能なら具体的な代替(コード断片・参照実装へのリンク)を添えます。ただし、設計判断が分かれる論点では、単一の解を指示するより選択肢とトレードオフを提示し、判断を作成者に返すほうが所有権を損ないません。確信が持てない指摘を断定形で書くことは、誤指摘のコストを受け手に転嫁する行為です。疑問は question として出します。

## 7. AI エージェントによるレビューの適用境界

本リポジトリのスキルが前提とする、AI エージェントがレビュアーを務める場合の境界条件を明示します。

- **入力の限界を成果物に明記する**: diff のみを入力とするレビューは、変更されなかったコード・実行時挙動・リポジトリ全体の設計文脈を見ていません。レビュー結果には「何を入力として何を確認したか(diff のみ/周辺コード込み/静的解析結果あり・なし)」を必ず記載します。静的解析結果が与えられていない場合、目視レビューのみであり §4.4 の片翼がない状態であることを明記します。
- **根拠のない所見を出力しない**: AI レビューの典型的失敗は、もっともらしいが誤った指摘(存在しない API 制約、当該言語では起きない挙動)を断定形で出すことです。§5.2 の根拠必須の原則を機械的に適用し、該当行と失敗シナリオを構成できない指摘は question に格下げするか、出力しません。
- **適合率(precision)を優先する**: 誤指摘が多いレビュアーは、静的解析の誤検知と同じ力学で無視されるようになります。網羅を演出するための低確度の指摘の量産は、レビューの信頼という資本を毀損します。件数の多さを成果としないことは、[品質メトリクスの落とし穴](./quality-metrics-pitfalls.md)のバグ件数の議論と同型です。
- **機械化可能な指摘へ退行しない**: lint・自動整形で検出できるスタイル指摘を AI レビューの成果として出力しません(§2.3・§4.4 の分担)。人間のレビュー時間と同様に、AI レビューの出力も設計・正確性・保守性の判断に集中させます。
- **実行はスコープ外**: 本リポジトリはレビューの手順・観点・出力契約(blueprint)を定義し、CI へのレビューボット組み込み・静的解析の実行・修正の適用は実行系が担います。なお、レビューコメントの自動解決支援など、レビュー工程への ML 適用は実運用が報告されています(Google, 2023)。
